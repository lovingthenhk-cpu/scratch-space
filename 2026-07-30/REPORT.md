## Part K: 共鳴点はそもそも「メモリの工夫」で届く距離だったのか、実際に計算する

前日 (2026-07-29) の「次回やろうとしていたこと」優先度1は次のように書か
れていた:

> **MITMのメモリ効率化**(...): 候補は (a) バケツの値を保存せず「mod D
> の値+復元用の最小限の情報」だけ持つ省メモリ化、(b) C言語での再実装
> ...。$s=28,A=65$・$s=59,A=137$ が具体的な次のターゲット

これは暗に「メモリの持ち方を工夫すれば8GBに収まるかもしれない」という
前提を含んでいたので、まずその前提自体を数値で検証した。

$(s,A)=(28,65)$ で対称分割($k=\lceil s/2\rceil=14$)を組んだ場合、
前半(または後半)の項数は次の通り:

```
|S1| = |S2| = C(51, 14) = 1,293,938,... ≈ 1.293×10^12 通り
```

(`resonance_feasibility.py` 参照、`math.comb` で厳密に計算)。これは
**1項1バイトという物理的に不可能な下限**を仮定しても

```
1.293×10^12 バイト ≈ 1,293 GB
```

であり、このセッションの8GB上限の**約160倍**、今回実測したメモリ効率的
な実装(dict索引、~150バイト/項、後述Part L/M参照)なら**約19万GB**に
達する。「メモリの持ち方」をどれだけ工夫しても、桁が3〜5桁違う。これは
メモリチューニングの問題ではない。

さらに、この分割方式(2-way MITM)が達成できる**最良の時間計算量**
(=対称分割の総項数 $2\times\binom{51}{14}$)を、真の総当たり
$\binom{A-1,s-1}=\binom{64,27}$ と比較すると:

```
brute force:        C(64,27)      = 846,636,978,475,316,672  ≈ 8.47×10^17
2-way MITM (最良):  2*C(51,14)    = 2,585,412,349,800         ≈ 2.59×10^12
speedup factor:                                                ≈ 327,000倍
```

MITM自体は本物の(平方根的な)高速化を達成しているが、それでもなお
$2.59\times10^{12}$項を**生成するだけ**で(結合処理を含めない最良ケース
でも)、実測ストリーミング速度 $\sim10^6$項/秒(後述Part M)からは

```
2.585×10^12 / 10^6 秒 ≈ 2.585×10^6 秒 ≈ 29.9日(単一コア、生成のみ)
```

かかる計算になる。これは「物理的に不可能」ではないが(実際、辞書結合の
オーバーヘッドを含めれば実際には数ヶ月規模になる)、**1回のセッション
(最大でも数十分〜数時間)には到底収まらない**。

さらに次の収束分数 $(s,A)=(59,137)$、$(146,339)$ になると:

```
s=59,  A=137: 対称分割の小さい方の辺 ≈ 1.225×10^26 通り
              → 1バイト/項でも 1.225×10^17 GB
s=146, A=339: 対称分割の小さい方の辺 ≈ 4.186×10^66 通り
              → 1バイト/項でも 4.186×10^57 GB
```

これはもう「メモリ」でも「時間」でもなく、**宇宙に存在する原子の数
規模を超える**次元の話であり、2-way MITMという方法そのものが原理的に
届かない(有限の意味では届くが、実務的には無限大と同じ)。

**結論(前日の記述の訂正)**: 前日のPROGRESS.mdの「MITMのメモリ効率化」
という優先度1の書き方は、まるでメモリの持ち方を工夫すれば
$(s,A)=(28,65)$ に手が届くかのような期待を持たせる書き方だったが、
これは不正確だった。正しくは:
- $(28,65)$: メモリの工夫だけでは届かないが、**時間を犠牲にする専用の
  長期バックグラウンド計算**(数十日〜数ヶ月規模)を割り当てれば理論上
  は届く距離(下記Part Pで将来の選択肢として記録)。
- $(59,137)$ 以降: 2-way MITMという方法そのものが原理的に届かない距離。
  別の方法(下記Part O、文献の手がかり)が必要。

## Part L: 素朴な「メモリ削減」の試みが逆効果になった話(失敗の記録)

前日のコード(`../2026-07-29/mitm_cycle_search.py`)は、両方の半分
(S1, S2)を完全にメモリ上の `dict: 総和 -> [値のリスト]` として保持して
から結合していた。これは「両方を同時に持つ必要はなく、片方だけ索引化
して、もう片方はストリーム(生成しながら都度チェックして捨てる)すれば
ピークメモリが半分になるはず」という直感に基づき、最初の実装
(`mitm_streaming.py` の最初のバージョン、下記の失敗の記録として
docstring内にも残してある)を書いた。

**結果は逆だった**: $s=16, A=36$ (対称分割、両辺とも約310万項)で
ベンチマークすると:

```
旧実装(両方保持):        peak RSS =  273.3 MB, time =  9.81s
新実装 v1(片方だけ索引化): peak RSS =  511.9 MB, time = 17.41s
```

**メモリが2倍近く悪化し、時間も2倍近く悪化した**。原因を切り分けると
2つあった:

1. **再帰ジェネレータの `yield from` チェーンのオーバーヘッド**:
   `parts` 個の入れ子になったジェネレータフレームを、1項生成するたびに
   全部通過する必要があり、CPythonでは深さに比例したオーバーヘッドが
   かかる(→ Part Mで明示的スタックのイテレータに書き換えて解消)。
2. **「万一の衝突に備えて」全ての値を毎回リストで包んでいた**こと、
   さらに `dict: 総和 -> {mod D の値: [値のリスト]}` という二重の入れ子
   構造にしていたこと。実際には(Part M参照)衝突はほとんど起きないのに、
   全項について「小さいリストオブジェクト + 辞書エントリ + 総和ごとの
   サブ辞書オブジェクト」という何重ものオーバーヘッドを毎回払っていた。
   フラットなリストへの追記(旧実装)は、Pythonの内部実装上これよりずっと
   安い。

さらに単純な「タプルキー `(B, V%D)` を使った1段のフラット辞書」に直して
も($s=16,A=36$ で同じ片側を索引化)、まだ旧実装の合計(273MB, 両側)より
悪化した(片側だけなのに414MB)。**辞書による索引化は、生の値をリストに
積むより本質的に高くつく**ということが、複数の変種を試した末に判明した
(索引には「探索用のキー」と「実際の値」の両方を保持する必要があるため、
1項あたり実質2つの大きい整数オブジェクトを払うことになり、フラットな
リストの「値だけ」保持する場合の2倍以上になる)。

これは今回のセッションで最も時間を使った、しかし記録する価値のある
**否定的な結果**である: 「両方保持 → 片方だけ索引化してストリーム」と
いう直感的なアイデアは、辞書のオーバーヘッドがフラットリストの節約分を
上回ってしまうため、**対称分割のままでは効かない**。

## Part M: 実際に効いた改善 ― 非対称分割 + ストリーミングでメモリを時間と交換する

Part Lの失敗を踏まえて設計し直した。ポイントは2つ:

1. **索引構造の最適化**: `dict: (総和, mod D の値) -> 値` という1段の
   フラット辞書にし、**衝突が実際に起きた場合だけ**その場でリストに
   昇格させる(「衝突は稀」という前提を、実際にデータで確認した上で
   採用 — 下記の実測値参照)。
2. **本質的な改善はここ**: 旧実装は常に対称分割($k=\lceil s/2\rceil$、
   両辺をほぼ同じ大きさにする)を使っていたが、これは**時間**を最小化
   する分割であって、**メモリ**を最小化する分割ではない。ストリーミング
   設計では、ピークメモリを決めるのは「小さい方の辺(索引化する側)」
   だけであり、大きい方の辺(ストリームする側)はメモリコストがほぼ
   ゼロになる。つまり **$k$ をわざと非対称にして、小さい方の辺をどこまで
   も小さくできる**(トレードオフとして大きい方の辺が増え、生成に
   かかる時間は伸びる)。これは分割のパラメータであって、網羅性(全形状
   を漏れなく検証すること)には一切影響しない — 単なる計算の順序の選択。

`choose_k_for_memory_budget(s, A, budget)` という関数を実装し、
「索引化する側の項数が `budget` 以下」という制約の下で「ストリームする
側(=時間コスト)が最小になる $k$」を選ぶようにした(`math.comb` だけで
安く計算できる見積もりを使うので、実際に列挙する前に判断できる)。

**実測(すべて独立したサブプロセスで測定 — 同一プロセス内で複数回測ると
`resource.getrusage` の `ru_maxrss` はプロセス開始からの単調非減少の
最大値なので、前の測定のピークが残ってしまい正しく比較できないことに
最初気づかず1回落とし穴にはまった。個別サブプロセスに直してから正しい
数字が出た)**、$s=16, A=36$ で:

| 分割 $k$ | 索引化する側の項数 | ストリームする側の項数 | 実測ピークRSS | 実測時間 |
|---|---|---|---|---|
| $k=8$(対称) | 3,108,105 | 3,108,105 | **542.8 MB** | 12.80s |
| $k=6$ | 230,230 | 30,045,015 | **41.8 MB** | 27.05s |
| $k=5$ | 53,130 | 84,672,315 | **16.4 MB** | 74.47s |

対称分割から $k=6$ に変えるだけで **メモリが約13倍減り**(542.8MB →
41.8MB)、時間は約2倍で済んだ。$k=5$ まで非対称にすると **メモリは
約33倍減り**(542.8MB → 16.4MB)、時間は約6倍。これは旧実装(常に
対称分割、両方保持)に対する**実質的な改善**であり、Part Lの失敗とは
違って本物の効果がある: 時間の余裕(バックグラウンド実行で数十分〜
数時間使える)とメモリの上限(8GB固定)というこのセッションの実際の
制約構造に合わせて、ダイヤルを回せるようになった。

## Part O: 文献の手がかり ― John Simons (2008) の一般化版バウンド

WebSearchを使い、$q=5$ の $h=4$ 未解決問題そのものが既に文献で解決/
制約されていないかを再確認する過程で、重要な手がかりを見つけた。

Simons & de Weger (2005, *Mathematics of Computation* 74, "Theoretical
and computational bounds for m-cycles of the 3n+1-problem") は、$q=3$
専用ではあるが、Laurent–Mignotte–Nesterenko (1995) の**2つの対数の
一次形式に対する明示的下界定理**(Baker型、一般の代数的数の対に対して
成り立つ一般定理であり $q=3$ に限らない)を使い、非自明サイクルの長さ
$K$ に対する明示的な上界を導出し、既知の連分数の情報と組み合わせて
非存在を証明する、という手法を確立している(WebFetchで原論文PDF
(ams.org、オープンアクセス)を直接確認: Lemma 6 で
$\log\Lambda \geq -24.34 D^4 \log A_1 \log A_2 (\ldots)^2$ という形の
明示的下界を使い、$\Lambda=(K+L)\log2-K\log3$ に適用して $K<86{,}000$
を得て、連分数の情報($K+L>357{,}638{,}239$)と矛盾させて非存在を示す、
という構造)。論文自身の Remark 4 が「この論法は $px+(p-2)r$ 型の問題
一般に(すなわち $q=3$ 以外にも)適用できる」と明記している。

さらに検索で見つけた **John L. Simons, "On the (non-)existence of
m-cycles for generalized Syracuse sequences", Acta Arithmetica 132
(2008)**(EUDMLのメタデータで確認: MSC分類に "11J86 Linear forms in
logarithms; Baker's method"、キーワードに "generalized Collatz problem,
cycle existence, linear forms in logarithms" とある)は、タイトルと
メタデータから判断する限り、まさにこの手法を**一般の $q$ に拡張した**
論文だと強く推測される。もしそうなら、私たちが2026-07-27から手作業の
全数探索(トラジェクトリ・サイクル方程式・MITM)で攻めている
$q=5, h=4$ の問題に対して、**既に文献上に明示的な有限上界(あるいは
非存在の証明そのもの)が存在する可能性がある**。

**今回はこの論文の本文を入手できなかった**(ResearchGateのページは
繰り返し429エラー、他のオープンアクセスの写しも見つからなかった)。
これは重要な未解決の宿題として次回以降に持ち越す(下記「次回やろうと
していること」参照)。**自分でBaker型の下界を導出することはあえて
しなかった** — Laurent–Mignotte–Nesterenko型の定理は $D$(代数体の
次数)、$A_1,A_2$(修正された高さ)、$\rho$ など複数のパラメータの
定義を正確に踏まえないと簡単に誤った定数を使ってしまう分野であり、
今回のセッションの範囲でこれを「専門家によるチェックなしに」実装して
結果を主張するのは、まさにこのプロジェクトが2026-07-27・2026-07-29に
繰り返し反省してきた「確認していないことを確認したかのように書く」
の同じ失敗パターンを、証明という最も重い主張で繰り返すリスクがある
と判断した。したがって、今回は文献の存在と出典だけを正確に記録し、
数値的な主張は一切していない。

## 環境メモ(前日までの内容に追記)

- **ベンチマークはサブプロセスで**: `resource.getrusage(...).ru_maxrss`
  はプロセス開始からの単調非減少の最大値。同一プロセス内で複数の
  設定を順に試すと、後の(小さいはずの)測定に前の(大きい)ピークが
  残ってしまい、誤った比較になる。異なる設定を比較するときは必ず
  別々のサブプロセスで測ること(`bench_child_*.py` 参照)。
- **ストリーミング実装にはタイムアウト機構がない**: `_enumerate_half_stream`
  ベースの関数は、呼び出したら最後まで走る。巨大な $(s,A)$ を誤って
  直接呼ばないよう、必ず `math.comb` ベースの安価な見積もりで事前に
  フィルタしてから呼ぶこと(`choose_k_for_memory_budget` と
  `run_production_streaming.py` の事前チェック参照)。
- **辞書 vs フラットリストのオーバーヘッド**: 今回の実測では、辞書
  (ハッシュテーブル)による索引化は、素朴に見積もった以上にフラット
  リストへの追記よりずっと高くつくことが分かった(項の値そのものに
  加えて探索キーも保持する必要があるため、実質2倍以上)。今後
  「メモリを削るために辞書をやめてソート済み配列+二分探索にする」
  というアイデアも一考の価値がある(今回は時間の都合で未実装 ―
  優先度は上記リストには入れていないが、Part Oの文献が空振りだった
  場合の代替候補として頭の片隅に置いておく)。
