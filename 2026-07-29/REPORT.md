  ており、我々の $T_q$ 写像とは別物である。
- **meet-in-the-middle をサイクル方程式に適用した先行研究も見つからなか
  った**。既存の計算的アプローチ(Hercherの分岐限定法、Barinaの全数検証、
  Roosendaalの連分数ベースの下界)はいずれも異なる技法であり、
  「形状の組を前半・後半に分割してハッシュ結合する」という部分は独自
  実装として問題なさそうという判断に至った。

以上を踏まえ、本日は (1) MITM実装(下記)を主軸とし、(2) 連分数アプローチ
は「最初の探索的な一歩」(証明ではない)として付随的に行うこととした。

### 手法: Meet-in-the-middle

`cycle_equation.py`(2026-07-28)の閉形式

$$n_1 = \frac{c_{s+1}}{2^A - q^s}, \qquad c_{s+1} = \sum_{i=1}^{s} q^{s-i} 2^{B_i}
\quad (B_1=0,\ B_{i+1}=B_i+a_i)$$

を、奇数項の位置 $i$ を前半($i=1,\ldots,k$)と後半($i=k+1,\ldots,s$)に分
割すると、

$$c_{s+1} = V_1(a_1,\ldots,a_k) + 2^{b} \cdot W(a_{k+1},\ldots,a_s), \qquad
b = B_{k+1} = a_1+\cdots+a_k$$

と分解できることに着目した($V_1$ は前半の組のみに、$W$ は後半の組(相対
オフセット)のみに依存)。$D=2^A-q^s$ は奇数($q$ が奇数のため)なので $2$
は $D$ を法として可逆であり、サイクルが閉じる条件 $D \mid c_{s+1}$ は

$$W \equiv -V_1 \cdot (2^b)^{-1} \pmod{D}$$

という**部分和問題(subset-sum)型のマッチング条件**に帰着する。そこで:

1. 前半の組を全て列挙し、$b$(分割点までの2進累積回数)ごとにバケツ分け
   して $V_1$ の値を保存する。
2. 後半の組を全て列挙し、後半の総halving回数 $A_2=A-b$ ごとにバケツ分け
   して $W$ の値を保存する。
3. 各 $b$ について、対応するバケツ同士をハッシュ結合し、上記合同式を満た
   す組を厳密な整数演算で特定、さらに独立な前向きシミュレーション
   (`_forward_reconstruct_and_check`、`cycle_equation.py` の
   `verify_cycle` とは別に、候補 $n_1$ から**ゼロから**軌道を再構築して
   閉じるか確認する二重検証)で確定させる。

これにより、単純な全数列挙が $\binom{A-1,s-1}{}$(組合せ爆発)であるのに
対し、本手法は $O\!\left(\binom{A-(s-k)}{k} + \binom{A-k}{s-k}\right)$
(2つの「半分」を別々に列挙してハッシュ結合するだけ)に落ちる。バランス
の良い分割($k\approx s/2$)では、これは古典的な部分和問題のMITM高速化と
同種の、指数を約半分にする削減である。

実装の詳細・複雑度の導出は `mitm_cycle_search.py` のdocstringに記載。

### 実装上の発見(パフォーマンス): ハッシュテーブル構築側の選び方

ベンチマーク中に判明した点として、$s$ が奇数のとき前半・後半どちらに
「余りの1項」を割り当てるかで実行時間が最大3.7倍変わることを確認した
($s=9, A=70$ で同じ総アイテム数(667,040+8,936,928)にもかかわらず、
$k=4$ で24.5秒、$k=5$ で6.7秒)。原因は、結合ループが毎回「後半バケツ」
からハッシュテーブルを再構築するため、後半バケツが小さい方(前半に多い
項数 $k=\lceil s/2\rceil$ を割り当てる)が有利なため。これは漸近計算量を
変えるものではなく、純粋なハッシュテーブル構築のオーバーヘッドの違いだ
が、実運用上は無視できない差なので `mitm_search_one_A` のデフォルト分割
に反映した(詳細は同ファイルのコメント参照)。

### 誠実な限界の明記

- これは Santos (2020) の未解決問題を解決するものではない。$s\geq19$
  の領域、および上表より大きい $A$ の領域は依然として未探索である。
- 各 $s$ で到達できた $A_{\max}$ は、Pythonの純粋な実装のCPU/メモリ効率
  によって制約されている。$s$ が大きくなるにつれ到達できる $A_{\max}$
  (ひいては総長 $L$)が縮小していく傾向がある(表参照)ため、「あらゆる
  $s$ に対して均等に深い網羅」ができているわけではない。
- 前日同様、この手法は「トラジェクトリ探索(値ベース)」とは独立な軸
  (「サイクルの構造」)での網羅性を提供するものであり、両者を合わせても
  無限に広い未探索領域が依然として残っている。

## Part J(付随・探索的): $\log_2 5$ の連分数解析

文献確認で「$q=5$ に連分数機械を適用した研究は見当たらない」と判明したた
め(Part I参照)、**証明ではなく最初の探索的な観察**として、
$\log_2 5=2.32192809\ldots$ の連分数展開と収束分数を計算した
(`log2_5_continued_fraction.py`、出力は `log2_5_cf_output.txt`)。

CF展開: $[2; 3, 9, 2, 2, 4, 6, 2, 1, 1, 3, 1, 18, 1, 6, \ldots]$

収束分数 $A/s$(小さい方から): $(2,1), (7,3), (65,28), (137,59),
(339,146), (1493,643), \ldots$

**観察**: 既知の2つの非自明 $q=5$ サイクル(いずれも $s=3,\ A=7$)は、
まさに収束分数 $(7,3)$ ―― $\log_2 5$ の最良の小さい有理近似 ―― にちょう
ど一致している。これは(新しい数学的事実ではないが)$q=3$ の理論
(Eliahou、Halbeisen–Hungerbühlerら)が示す「サイクルは $\log_2 q$ の良い
有理近似の近く($2^A\approx q^s$)に集中しがち」という定性的描像が、
$q=5$ の具体的な既知サイクルでもきれいに成立していることを直接確認した
形になる。

これは次の収束分数 $(65,28)$、$(137,59)$、$(339,146)$ 付近が「もし
$h=4$ の非自明サイクルが存在するなら、その総サイクル長が近くにありそう
な、優先的に調べるべき箇所」であることを示唆する(ただし、これは「その
形状であれば整数解になりやすい」という定性的な優先順位付けに過ぎず、
厳密な排除や存在の証明には全くならない点に注意)。

### 共鳴点 $s=28,\ A=65$ への挑戦とメモリ制約による失敗

上記の示唆に基づき、$s=28,\ A=65$(2番目の収束分数)へのMITM探索を試み

anon-rss:7425024kB`)。原因は、$k=14$ の分割で前半・後半のバケツに数百万

現在の素朴なPython実装の具体的な限界として明記しておく。C言語での再実装
(固定幅整数配列を使う、あるいは値を保存せず都度再計算するなど)であれば
克服できる可能性が高いが、今回はそこまでは着手していない。

  なり、同じ総アイテム数でも最大3.7倍速くなる。`mitm_search_one_A` の
  デフォルトはこれを反映済み。
- **メモリはCPU時間と並ぶ独立したボトルネック**(今回新たに確認): 今まで
  の環境メモはCPU時間・タイムアウトの話が中心だったが、MITMのように
  「大量の値をハッシュテーブルに保持する」設計では、8GB RAM上限の方が
  先に問題になりうる。次回以降、大きな $(s,A)$ を狙う際は事前に
  `_enumerate_half` の予想サイズ(`math.comb`で概算可能)を確認し、
  「アイテム数 × 数十〜百バイト」がRAM上限に収まるか見積もってから実行
  すること。
- 2コア, 8GB RAM 環境、gcc 13.3, Python 3.11.15 は前日と同様。
  `mpmath` は今回新規にpipインストールが必要だった
  (`pip install mpmath --break-system-packages`)。
